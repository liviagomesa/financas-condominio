# Research: Duplicar lançamentos para o mês seguinte

Não há nenhum `NEEDS CLARIFICATION` pendente no Technical Context: stack, versões e ferramentas de teste são reaproveitadas integralmente das features 001–006 (Constituição, Princípio III). As decisões abaixo cobrem os pontos de design específicos desta feature.

## Nova ação de negócio dedicada `POST /api/accounts/{id}/duplicate`, seguindo o mesmo padrão já usado por `/pay`

- **Decision**: A duplicação é exposta como `POST /api/accounts/{id}/duplicate`, recebendo um corpo `AccountDuplicateRequest(boolean zeroAmount)` e retornando `201 Created` com o `AccountResponse` da cópia recém-criada — mesmo formato de resposta já usado por `POST`/`PUT`/`/pay`. O frontend chama esse endpoint uma vez por lançamento selecionado (nunca em lote no backend), reaproveitando o padrão de melhor esforço já estabelecido pela remoção em lote (`bulkDelete`).
- **Rationale**: A Constituição (Princípio VI) já define esse padrão de rota — `POST /{recurso}/{id}/{ação}` — para qualquer ação de negócio dedicada que não seja nem `PUT` completo nem `POST` de criação simples, citando `POST /api/accounts/{id}/pay` como exemplo. Duplicar um lançamento existente para gerar outro é exatamente esse caso: não é uma edição do recurso original (`PUT`) nem uma criação a partir de dados soltos informados pela usuária (`POST` no recurso plano) — é uma ação sobre um recurso já existente que produz um novo recurso. Um corpo de requisição (em vez de query param) mantém consistência com `AccountPaymentRequest`, que também carrega um único campo (`paymentDate`) como corpo de uma ação de negócio.
- **Alternatives considered**: duas rotas separadas (`/duplicate` e `/duplicate-zeroed`) — rejeitada por introduzir duas rotas para uma única regra de negócio que difere apenas por um flag booleano, quando o próprio padrão de `AccountPaymentRequest` já mostra que um corpo com um campo é idiomático neste projeto; usar `POST /api/accounts/bulk-duplicate` recebendo uma lista de ids — rejeitada por fugir do padrão de melhor esforço já estabelecido (`bulkDelete`, que também não tem endpoint transacional em lote) e por exigir um contrato de resposta parcial (sucesso/falha por item) que o backend não modela em nenhum outro lugar do projeto hoje.

## `AccountService.duplicate` não precisa de `@Transactional` — é uma única escrita

- **Decision**: `AccountService.duplicate(Long id, boolean zeroAmount)` lê o lançamento original (`findById`, já existente) e executa um único `repository.save(new Account(...))` com os campos copiados e ajustados. Nenhuma anotação `@Transactional` é necessária.
- **Rationale**: Princípio II é objetivo: `@Transactional` só é exigido quando o método executa mais de uma operação de escrita. `duplicate` faz exatamente um `save`, assim como `create`/`registerPayment` hoje, que também não são `@Transactional`.
- **Alternatives considered**: nenhuma — critério já definido pela Constituição, sem ambiguidade a resolver aqui.

## Cálculo do "mês seguinte" usa `LocalDate.plusMonths(1)` diretamente, sem função auxiliar

- **Decision**: A nova data de vencimento é `original.getDueDate().plusMonths(1)`, chamado diretamente dentro de `duplicate`, sem método auxiliar dedicado.
- **Rationale**: O Javadoc de `java.time.LocalDate.plusMonths` já implementa exatamente a regra descrita no Edge Case do spec ("quando o dia não existe no mês seguinte, cai no último dia válido") — por exemplo, 31/01 + 1 mês = 28/02 ou 29/02 em ano bissexto — sem necessidade de tratamento manual de overflow. Como a chamada é uma única linha sem lógica condicional, extrair um método privado só para isso seria uma indireção sem ganho de legibilidade ou reuso.
- **Alternatives considered**: implementar o ajuste de dia manualmente (`YearMonth.from(dueDate).plusMonths(1).atEndOfMonth()` com fallback) — rejeitada por já existir pronta na biblioteca padrão, sem necessidade de reinventar.

## O lançamento duplicado não guarda vínculo com o original

- **Decision**: A cópia criada por `duplicate` é uma `Account` nova e independente — nenhuma coluna nova (ex.: `duplicated_from_id`) é adicionada à tabela `account`, e nenhuma migration é necessária nesta feature.
- **Rationale**: O spec já deixa isso explícito nos Key Entities ("sem vínculo entre original e cópia após a criação") e nenhum requisito funcional depende de rastrear a origem de uma cópia. Adicionar uma coluna de rastreabilidade seria complexidade não solicitada.
- **Alternatives considered**: coluna `duplicated_from_id` nullable, auto-referenciando `account.id` — rejeitada por não haver nenhum requisito (relatório, filtro, exibição) que precise dessa informação; pode ser revisitada no futuro se a usuária pedir explicitamente.

## `BulkActionsBar` ganha duas ações extras opcionais, sem afetar as outras três listagens que a reaproveitam

- **Decision**: `shared/components/bulk-actions-bar/bulk-actions-bar.ts` ganha um novo input opcional `showDuplicateActions = input<boolean>(false)` e dois novos outputs, `duplicate = output<void>()` e `duplicateZeroed = output<void>()`. O template só renderiza os dois botões novos ("Duplicar para o mês seguinte" / "Duplicar para o mês seguinte (valor zerado)") quando `showDuplicateActions()` é `true`. Só `account-list.html` passa `[showDuplicateActions]="true"`; `party-list`, `fund-list` e `group-list` continuam usando o componente exatamente como hoje, sem nenhuma alteração de template ou comportamento (o input novo tem valor padrão `false`).
- **Rationale**: A Constituição exige reaproveitar `BulkActionsBar` em vez de reimplementar a barra de ações numa tela nova — mas essa é a primeira feature em que uma ação em lote não se aplica a todas as quatro listagens que a reaproveitam (só contas têm vencimento/valor duplicável, ver Assumptions do spec). Um input booleano com valor padrão `false` é a menor mudança aditiva possível: estende o componente compartilhado sem quebrar nem exigir alteração nas outras três telas.
- **Alternatives considered**: criar um componente novo (`AccountBulkActionsBar`) específico para contas — rejeitada por duplicar a estrutura visual e o botão "Remover selecionados" já existentes em `BulkActionsBar`, contrariando o princípio de reaproveitar o trio já estabelecido; passar um `ng-content`/slot genérico para ações arbitrárias — rejeitada por ser mais complexidade do que o caso atual (duas ações fixas, não arbitrárias) exige.

## Duplicação em lote no frontend segue o mesmo padrão de "melhor esforço" de `bulk-delete.ts`, num arquivo dedicado novo

- **Decision**: Novo arquivo `shared/bulk-duplicate.ts`, com uma função `bulkDuplicate(ids: number[], duplicateFn: (id: number) => Observable<Account>): Observable<BulkDuplicateResult>`, estruturalmente idêntica a `bulkDelete` (mesmo uso de `forkJoin` + `catchError`, mesmo formato de resultado `{ succeeded, failed }`), mas retornando os `Account` criados em vez de `void`.
- **Rationale**: Mantém o mesmo padrão de melhor esforço já usado pela remoção em lote (FR-007 do spec exige exatamente esse comportamento: falhas parciais não impedem as demais duplicações). Um arquivo dedicado — em vez de generalizar `bulk-delete.ts` num helper genérico `bulkAction<T>` reaproveitado por ambos — evita tocar um utilitário hoje usado pelas quatro listagens (`account-list`, `party-list`, `fund-list`, `group-list`) só para acomodar uma necessidade nova de uma única tela, reduzindo o raio de impacto desta feature.
- **Alternatives considered**: generalizar `bulk-delete.ts` para um `bulkAction<T>(ids, actionFn)` genérico, com `bulkDelete`/`bulkDuplicate` como casos específicos — considerada por eliminar duplicação de estrutura, mas descartada por exigir alterar um arquivo já estável e usado por todas as listagens, um risco desproporcional ao ganho (poucas linhas idênticas) para esta feature; pode ser revisitado numa revisão de constituição futura se um terceiro caso de uso similar aparecer.

## Atalho de teclado Ctrl+C / Ctrl+V memoriza a seleção via `HostListener` de `document`, com guarda de foco

- **Decision**: `account-list.ts` ganha um `signal<number[]>([])` chamado `copiedIds` e um único método `@HostListener('document:keydown', ['$event']) onKeydown(event: KeyboardEvent)`. Dentro dele: se `document.activeElement` for um `INPUT`/`TEXTAREA` ou tiver `isContentEditable`, o método retorna imediatamente sem fazer nada (FR-011, preserva copiar/colar nativo da edição inline). Caso contrário: `Ctrl+C` com `selection.selectedIds().size > 0` grava `copiedIds.set(Array.from(selection.selectedIds()))`; `Ctrl+V` com `copiedIds().length > 0` chama `event.preventDefault()` e dispara a mesma duplicação (valor mantido) usada pelo botão, mas sobre `copiedIds()` em vez da seleção atual (FR-009). `copiedIds` não é limpo após o `Ctrl+V`, permitindo colar mais de uma vez — mesmo comportamento de um clipboard real.
- **Rationale**: `HostListener` em `document` (em vez de um listener local no elemento da tabela) garante que o atalho funcione independentemente de qual elemento da página está focado no momento, desde que não seja um campo editável — exigência implícita de FR-009 ("com um ou mais lançamentos selecionados"), já que o foco pode estar em qualquer lugar da tela quando a usuária pressiona Ctrl+C. A guarda de foco por `activeElement` é a forma mais direta de não interferir com o copiar/colar nativo do campo de edição inline de valor (introduzido na feature 006), sem precisar marcar manualmente cada campo com um `stopPropagation`.
- **Alternatives considered**: usar `(keydown)` no template do componente em vez de `HostListener` de `document` — rejeitada porque o elemento raiz do componente só recebe eventos de teclado quando algo dentro dele está focado, o que não é garantido (ex.: foco em nenhum elemento interativo, ou em outro componente da página); limpar `copiedIds` automaticamente após o primeiro `Ctrl+V` — rejeitada por não haver pedido nesse sentido e por contrariar a metáfora de clipboard que a própria usuária usou para descrever a funcionalidade.

## Cobertura de teste automatizado desta feature

- **Decision**: Backend — `AccountServiceTest` ganha casos novos para `duplicate`: mantém todos os campos exceto vencimento/pagamento/valor; soma um mês ao vencimento, incluindo o caso de virada de mês mais curto (31/01 → 28 ou 29/02); zera o valor quando `zeroAmount = true`; sempre grava `paymentDate = null`, mesmo que o original esteja pago; lança `NotFoundException` para id inexistente; não altera o lançamento original. Frontend — novo `shared/bulk-duplicate.spec.ts` (Vitest puro, mesmo padrão de `bulk-delete.spec.ts`), cobrindo sucesso total, falha parcial e lista vazia. A lógica de teclado (`onKeydown`, exclusão por `activeElement`) e a integração do botão em `account-list.ts` não recebem teste unitário dedicado, seguindo o precedente já registrado no `research.md` da feature 006 ("nenhum componente Angular tem hoje teste unitário próprio") — validadas manualmente via Playwright durante a implementação (Princípio III).
- **Rationale**: Mantém a mesma linha divisória já usada no projeto entre "lógica pura testada por Vitest/JUnit" e "orquestração de componente validada via Playwright", sem inaugurar uma exceção nova nesta feature.
- **Alternatives considered**: adicionar `account-list.spec.ts` cobrindo `onKeydown`/`performDuplicate` isoladamente com mocks — descartada pelo mesmo motivo já registrado na feature 006 (mudança de convenção fora do escopo desta feature).
