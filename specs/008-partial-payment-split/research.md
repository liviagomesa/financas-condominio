# Research: Pagamento Parcial de Contas

Não há nenhum `NEEDS CLARIFICATION` pendente no Technical Context: stack, versões e ferramentas de teste são reaproveitadas integralmente das features 001–007 (Constituição, Princípio III). As decisões abaixo cobrem os pontos de design específicos desta feature.

## O campo `paidAmount` é adicionado ao `AccountPaymentRequest` já existente, como opcional

- **Decision**: `AccountPaymentRequest` ganha um segundo campo, `BigDecimal paidAmount`, sem `@NotNull` mas com `@Positive(message = "O valor pago deve ser maior que zero.")`. Quando ausente (`null`), `AccountService.registerPayment` trata como "pagamento integral" (equivalente a `paidAmount = amount` da conta). Nenhuma rota nova é criada — `POST /api/accounts/{id}/pay` continua sendo a única ação de pagamento.
- **Rationale**: A Constituição (Princípio VI) já define `/pay` como a ação de negócio dedicada correta para registrar pagamento; adicionar um campo opcional ao corpo já existente é a menor mudança de contrato possível. Deixar o campo opcional (em vez de obrigatório, sempre preenchido pelo frontend) mantém o endpoint utilizável por qualquer chamador que só queira registrar a data de pagamento sem se preocupar em calcular o valor devido — o comportamento default (`null` = valor cheio) é o mesmo que o endpoint já tem hoje. `@Positive` (em vez de `@PositiveOrZero`, usado em `AccountRequest.amount`) rejeita tanto valores negativos (FR-008) quanto zero (FR-009) numa única anotação — a especificação da Bean Validation trata `null` como válido para `@Positive`, então o campo continua opcional mesmo com essa restrição.
- **Alternatives considered**: tornar `paidAmount` obrigatório, exigindo que o frontend sempre envie o valor da caixa — rejeitada por acoplar o contrato de API a uma decisão de UI (a caixa vir pré-preenchida) que pode mudar sem motivo para quebrar outros chamadores; um endpoint novo dedicado a pagamento parcial (`POST /{id}/pay-partial`) — rejeitada por introduzir duas rotas para uma única ação de negócio ("registrar pagamento"), quando a diferença entre pagamento integral/parcial/a maior é só o valor de um campo, não uma ação distinta.

## Numeração `- parte N` é derivada da própria `description`, sem coluna nova

- **Decision**: Nenhum campo novo (ex.: `partNumber`) é adicionado à entidade `Account`. Ao dividir uma conta, `AccountService` procura na `description` atual o padrão `" - parte N"` (regex `^(.*) - parte (\d+)$`, aplicado sobre o texto já persistido). Se não encontrar, a descrição-base é a própria descrição atual e o número atual é considerado inexistente (`N = null`); a conta sendo paga recebe `descrição + " - parte 1"`. Se encontrar, a descrição-base é o grupo antes do sufixo e o número atual é o valor capturado; a conta sendo paga **não** é renomeada (mantém seu sufixo). Em ambos os casos, a nova conta com o saldo restante recebe `descrição-base + " - parte " + (N atual + 1)`.
- **Rationale**: O spec (Assumptions) já rejeita explicitamente um relacionamento estrutural entre as contas de um split ("sem vínculo estrutural entre elas além do sufixo compartilhado na descrição") — o mesmo raciocínio se aplica a um contador: introduzir uma coluna só para numeração seria uma migration e um campo persistido para uma informação inteiramente derivável do texto já existente. Como só a conta pendente (nunca a já paga) pode ser dividida de novo (FR-006), a cadeia de splits é sempre linear — a conta sendo paga em qualquer split já é, por construção, a que tem o maior número usado até então nessa linhagem, então "número atual + 1" é sempre correto sem precisar consultar outras contas do banco.
- **Alternatives considered**: coluna `part_number` (inteiro, nullable) na tabela `account`, populada pelo backend — rejeitada pelo motivo acima (nenhum requisito além da própria numeração exibida na descrição depende desse valor; se o formato de exibição mudar no futuro, um campo persistido teria que migrar junto). Um contador global por "grupo de split" com uma coluna de agrupamento (`split_group_id`) — rejeitada pela mesma razão que o modelo de "ledger de pagamentos" foi descartado no próprio spec: complexidade desproporcional ao porte do projeto para uma necessidade puramente de exibição.
- **Risco aceito**: se a usuária editar manualmente a descrição de uma conta resultante de um split (ex.: apagar o "- parte 2" pelo formulário comum de edição), a próxima divisão dessa conta recomeça a numeração do zero (trata como se fosse a primeira parte). Risco cosmético, não financeiro — os valores em si nunca dependem do texto da descrição — e não há requisito pedindo proteção contra edição manual desse sufixo.

## `registerPayment` concentra as três faixas de valor pago (igual/menor/maior) e ganha `@Transactional`

- **Decision**: `AccountService.registerPayment(Long id, LocalDate paymentDate, BigDecimal paidAmount)` substitui a assinatura de dois argumentos atual (único ponto de chamada é `AccountController.pay`, então não há necessidade de sobrecarga). Dentro do método: `paidAmount` é resolvido para `account.getAmount()` quando vier `null`; a comparação com `compareTo` decide entre os três ramos do spec (FR-002/FR-003+FR-003a/FR-005). O ramo de divisão executa dois `save` (conta original truncada + nova conta do saldo restante), por isso o método inteiro é anotado `@Transactional` — mesmo os outros dois ramos, que fazem só um `save`, ficam dentro do mesmo método transacional, já que a anotação é por método, não por branch de execução.
- **Rationale**: Constituição, Princípio II — o critério para `@Transactional` é objetivo (quantidade de escritas que o método executa), não uma decisão caso a caso; como pelo menos um caminho de execução do método faz duas escritas sequenciais, o método precisa da anotação para não deixar a conta original truncada comitada sem a nova conta do saldo restante em caso de falha no meio do caminho. Manter a lógica das três faixas num único método (em vez de três métodos privados chamados por um método público fino) reflete que elas são, na visão do domínio, uma única operação de negócio ("registrar pagamento"), com resultado diferente conforme o valor informado — dividir em métodos separados só moveria a mesma decisão de lugar sem reduzir complexidade real.
- **Alternatives considered**: método público fino delegando para três métodos privados (`registerFullPayment`, `splitPartialPayment`, `registerOverpayment`) — considerada, mas descartada por esta feature ter uma única regra de decisão simples (comparação de dois `BigDecimal`) sem repetição entre os ramos que justificasse a extração; pode ser revisitada se a lógica crescer.

## Nota de pagamento a maior é montada manualmente, sem `NumberFormat.getCurrencyInstance`

- **Decision**: O texto acrescentado a `observations` no caso de pagamento a maior é montado como `"pago R$" + valor formatado com vírgula decimal + " a mais"` (ex.: `"pago R$1,00 a mais"`), sem espaço entre "R$" e o número. Quando `observations` já tem conteúdo, a nota é acrescentada numa nova linha (`existente + "\n" + nota`); quando está vazio/nulo, a nota se torna o conteúdo inteiro do campo.
- **Rationale**: `java.text.NumberFormat.getCurrencyInstance(new Locale("pt", "BR"))`, a forma "padrão" de formatar moeda em Java, insere um espaço (ou espaço não separável, dependendo da versão dos dados de locale da JVM) entre "R$" e o valor — o exemplo literal do spec ("pago R$1,00 a mais") não tem esse espaço. Formatar manualmente (vírgula decimal, duas casas) evita essa divergência de forma previsível, sem depender de dados de locale que podem variar entre JDKs.
- **Alternatives considered**: `NumberFormat.getCurrencyInstance` — rejeitada pelo motivo acima; sobrescrever o campo `observations` em vez de acrescentar — rejeitada porque contraria FR-005/Acceptance Scenario 2 explicitamente ("sem sobrescrever o que já estiver nesse campo, se houver algo").

## Cobertura de teste automatizado desta feature

- **Decision**: Backend — `AccountServiceTest` ganha casos novos para `registerPayment`: valor pago igual ao devido (comportamento inalterado, sem renomear nem criar conta); valor pago menor, sem sufixo prévio (renomeia para "parte 1", cria "parte 2" com o saldo, mesma data de vencimento, sem recorrência); valor pago menor, com sufixo prévio (mantém o nome da conta paga, cria a próxima parte numerada corretamente); valor pago maior (ajusta valor, registra nota em `observations` vazio e em `observations` já preenchido, sem sobrescrever); valor pago zero (nenhuma escrita ocorre — ver decisão de UI abaixo, mas o backend também rejeita via `@Positive`); valor pago negativo (rejeitado pela validação do DTO, testado via teste de contexto Spring/`@Valid` se já houver um padrão equivalente no projeto, ou documentado como comportamento do framework se não houver). Frontend — nenhum teste unitário novo dedicado ao componente (mesmo precedente das features 006/007); validação manual via Playwright dos três fluxos (integral, parcial, a maior) e da ausência da caixa no fluxo de "Alterar pagamento".
- **Rationale**: Mantém a mesma linha divisória já usada no projeto entre "lógica de negócio pura, testada por JUnit/Mockito" e "orquestração de componente Angular, validada via Playwright", sem inaugurar exceção nova nesta feature. Cobertura de regra de negócio nova é exigência explícita do Princípio III.
- **Alternatives considered**: nenhuma — critério de cobertura já definido pela Constituição para este tipo de mudança.

## Remoção completa do campo `recurring`, via `DROP COLUMN` simples (não uma renomeação)

- **Decision**: O atributo `recurring` é removido por completo de `Account` (campo, parâmetro de construtor, getter/setter), dos DTOs `AccountRequest`/`AccountBulkRequest`/`AccountResponse`, do formulário `account-form` e do model `account.model.ts`. Uma migration nova (`V14__drop_recurring_from_account.sql`) executa `ALTER TABLE account DROP COLUMN recurring;`. `AccountService.create`, `createForGroup`, `update` e `duplicate` perdem o parâmetro/uso de `recurring`; `registerPayment` (esta feature) nunca precisa mencioná-lo, porque ele deixa de existir.
- **Rationale**: Decisão explícita da usuária (ver spec.md § Assumptions/Clarifications, revisão durante o planejamento): o campo não decide nenhum comportamento hoje (confirmado por busca no código — nenhuma query, filtro ou regra de negócio lê `recurring`, ele só é copiado/exibido), e a próxima feature planejada é a automação real de lançamentos recorrentes (execução agendada), que será desenhada do zero. Manter o campo até lá exigiria que o split desta mesma feature o tratasse como caso especial (decisão original, já superada) só para um dado sem uso real. `DROP COLUMN` direto (em vez de uma migration que primeiro renomeia e depois remove) é apropriado porque não há generalização/renomeação de entidade envolvida — a cláusula da Constituição (Princípio I) que prefere `ALTER TABLE ... RENAME` a recriar-e-copiar pressupõe *dado real a preservar* numa renomeação; aqui não há renomeação nem dado com valor de negócio a preservar, então uma remoção direta e documentada (Princípio I, segunda cláusula) é suficiente.
- **Alternatives considered**: manter o campo e só desmarcá-lo nas contas resultantes de um split (decisão original desta feature) — descartada pela própria usuária por deixar um campo morto no sistema até a feature de cron, quando ele precisaria ser removido ou redesenhado de qualquer forma; renomear a coluna para algo como `_deprecated_recurring` em vez de remover — descartada por não haver nenhum consumidor (relatório, exportação) que dependa de preservar o dado, tornando a renomeação só uma remoção adiada sem benefício.

## A caixa de valor zero é bloqueada no frontend antes da chamada HTTP, mesmo padrão já usado para data vazia

- **Decision**: `confirmPayment` (frontend) continua com um guarda no início do método: além do já existente `if (!this.paymentDateDraft) return;`, um novo guarda impede a chamada quando a conta ainda está pendente e o valor pago digitado é vazio, não numérico, ou `<= 0` — sem exibir mensagem de erro, apenas ignorando o clique (mesmo comportamento silencioso já usado para data vazia).
- **Rationale**: FR-009 pede que a confirmação seja "ignorada" para valor zero, e o padrão já estabelecido no componente para um campo obrigatório vazio (`paymentDateDraft`) é exatamente esse retorno silencioso — reaproveitar o mesmo padrão evita introduzir uma mensagem de erro nova só para este campo, quando o restante do fluxo de pagamento não usa esse tipo de feedback.
- **Alternatives considered**: exibir uma mensagem de erro (como `amountEditError`, usado na edição inline de valor) — rejeitada por não haver pedido nesse sentido no spec, e por já existir um padrão silencioso equivalente no mesmo componente para o outro campo obrigatório do mesmo formulário inline (data de pagamento).
