# Research: Geração Automática de Contas Recorrentes

Não há nenhum `NEEDS CLARIFICATION` pendente no Technical Context: stack, versões e ferramentas de teste são reaproveitadas integralmente das features 001–008 (Constituição, Princípio III). As decisões abaixo cobrem os pontos de design específicos desta feature, incluindo os pontos resolvidos na sessão de `/speckit-clarify` (recuperação na inicialização, isolamento por cobrança, indicador de falha).

## `RecurringCharge` é uma entidade nova em pacote próprio, reaproveitando `AccountType`

- **Decision**: Novo pacote `com.financas.recurringcharge` (`api/`, `domain/`, `infra/`, espelhando a estrutura de `account`). A entidade `RecurringCharge` reaproveita o enum `com.financas.account.domain.AccountType` (`RECEIVABLE`/`PAYABLE`) em vez de duplicar um enum equivalente — o próprio spec descreve o campo como "mesmo discriminador receber/pagar de `Account`".
- **Rationale**: Duplicar o enum criaria duas fontes de verdade para o mesmo conceito de domínio, arriscando divergência futura (ex.: um terceiro tipo adicionado a um enum e esquecido no outro). O projeto já tem precedente de dependência cruzada entre pacotes de entidade quando faz sentido de domínio (`Account` depende de `Party`/`Fund`; `PartyService`/`FundService` já dependem de `AccountRepository` para bloquear remoção por vínculo — ver decisão abaixo) — importar `AccountType` de `account.domain` para `recurringcharge.domain` segue o mesmo padrão já aceito.
- **Alternatives considered**: enum duplicado `RecurringChargeType` em `recurringcharge.domain` — rejeitado pelo risco de divergência acima; mover `AccountType` para `shared/` — rejeitado porque a Constituição reserva `shared/` para recursos verdadeiramente transversais (`GlobalExceptionHandler`, exceptions genéricas, config técnica), e mover um enum já estável de `account` só para esta feature tocaria uma feature já implementada sem necessidade.

## Estado ativo/inativo é derivado de `deactivatedAt` (nullable), não um booleano `active` persistido à parte

- **Decision**: `RecurringCharge` não tem um campo `boolean active`. Em vez disso, tem `LocalDate deactivatedAt` (nullable) e um método derivado `isActive()` (`return deactivatedAt == null;`). Passa a valer `deactivatedAt = LocalDate.now()` tanto na remoção (FR-009) quanto na inativação da linha antiga numa edição (FR-008) — nunca `null` de novo depois de preenchido (não há "reativação").
- **Rationale**: Decisão revisada a partir de uma pergunta direta da usuária durante o planejamento. Segue diretamente o Princípio IV da Constituição — "um estado binário inteiramente derivável da presença/ausência de outro campo MUST ser derivado desse campo, nunca duplicado como um segundo campo booleano persistido" — mesmo padrão já estabelecido por `Account.isPaid()`, derivado de `paymentDate != null`. Um campo de data nula carrega estritamente mais informação que um booleano (também registra *quando* a linha deixou de ser vigente) sem custo adicional de modelagem. O nome `deactivatedAt` (em vez de `deletedAt`/`deletedDate`, cogitado inicialmente pela usuária) foi escolhido porque o mesmo campo cobre dois motivos distintos de inativação — remoção explícita (FR-009) e substituição por edição (FR-008) — e só o segundo caso não é, do ponto de vista da usuária, uma "exclusão"; "ativa"/"inativa" já é a terminologia usada pelo próprio spec.md para os dois casos igualmente.
- **Alternatives considered**: `boolean active` persistido (design original desta feature, antes da revisão) — rejeitado por duplicar um estado derivável, na contramão do Princípio IV; `deletedAt`/`deletedDate` (nome sugerido inicialmente) — descartado pela imprecisão semântica no caso de substituição por edição, explicada acima; dois campos separados (`deletedAt` + `supersededAt`) para diferenciar os dois motivos — rejeitado por não haver nenhum requisito que precise distinguir os dois casos (spec.md trata "deixar de aparecer na listagem"/"deixar de gerar contas" de forma idêntica para ambos), então dois campos seriam complexidade sem benefício.

## `Account` ganha uma FK opcional para `RecurringCharge`, criando dependência cruzada entre os dois pacotes (precedente já existente com `Party`)

- **Decision**: `Account` ganha o campo `private RecurringCharge recurringCharge;` (`@ManyToOne`, opcional, `@JoinColumn(name = "recurring_charge_id", nullable = true)`), com getter/setter — **não** um parâmetro de construtor novo. É preenchido só pelo processo de geração (`RecurringChargeGenerationService.generateOne`), via setter, depois de `new Account(...)` com os 8 argumentos já existentes.
- **Rationale**: Adicionar como 9º parâmetro do construtor obrigaria a tocar todos os pontos de chamada já existentes (`create`, `createForGroup`, `duplicate`, `registerPayment`) só para passar `null` — mudança mecânica ampla sem benefício, já que nenhum desses fluxos cria uma conta vinculada a uma cobrança recorrente. Um setter dedicado, chamado só no único lugar que efetivamente usa esse vínculo, é a menor mudança possível. Isso cria uma dependência de pacote `account.domain` → `recurringcharge.domain`; combinada com `recurringcharge.domain` → `account.domain` (necessária para o `AccountRepository` na checagem de idempotência, decisão abaixo), o resultado é uma dependência cruzada entre os dois pacotes — mesmo padrão já presente entre `party`/`account` hoje (`PartyService` depende de `AccountRepository` para `PartyHasAccountsException`, enquanto `Account` depende de `Party` como dono da FK), então não é uma violação nova da arquitetura em camadas, é a mesma forma de acoplamento já aceita no projeto.
- **Alternatives considered**: campo solto `Long recurringChargeId` sem FK de banco de verdade — rejeitado pelo próprio Princípio I ("nunca um campo id solto sem FK de banco de verdade" para vínculos obrigatórios; aqui o vínculo é opcional mas o mesmo raciocínio de integridade referencial se aplica); tabela de log/auditoria separada relacionando conta gerada → molde — rejeitada por complexidade desproporcional quando uma FK nullable já resolve tanto a rastreabilidade quanto a checagem de idempotência.

## Idempotência (FR-006) via `existsByRecurringChargeIdAndDueDateBetween`, não por comparação de outros campos

- **Decision**: `AccountRepository` ganha `boolean existsByRecurringChargeIdAndDueDateBetween(Long recurringChargeId, LocalDate start, LocalDate end)`. Antes de gerar, o serviço calcula o mês-alvo (`YearMonth`) e chama esse método com o primeiro e o último dia daquele mês — como o `dueDate` de qualquer conta gerada está sempre dentro do mês-alvo por construção (FR-007), essa janela identifica exatamente "já existe conta gerada deste molde para este mês/ano".
- **Rationale**: O próprio input do spec já rejeita explicitamente inferir isso "comparando outros campos" — a referência direta (FK) é a fonte de verdade. Uma janela de datas (`Between`) evita precisar de uma coluna redundante `targetYearMonth` na tabela `account` só para essa checagem.
- **Alternatives considered**: coluna `target_year_month` (String/YearMonth) persistida em `Account` — rejeitada por ser dado derivável do próprio `dueDate` já persistido, sem necessidade real fora dessa checagem pontual.

## Cálculo do mês-alvo unifica o agendamento fixo (FR-004) e a recuperação na inicialização (FR-015) num único método

- **Decision**: Um único método, `resolveMostRecentDueTargetMonth(LocalDate reference)`, decide o mês-alvo a partir de uma data de referência: `reference.getDayOfMonth() >= 25 ? YearMonth.from(reference).plusMonths(1) : YearMonth.from(reference)`. O agendamento fixo (`@Scheduled(cron = "0 0 6 25 * *", zone = "America/Sao_Paulo")`) e o listener de recuperação (`@EventListener(ApplicationReadyEvent.class)`) chamam exatamente o mesmo método público, `generatePendingAccounts()`, sem nenhuma lógica duplicada ou "modo" diferente entre os dois gatilhos.
- **Rationale**: Como o cron só dispara exatamente às 6h do dia 25, `resolveMostRecentDueTargetMonth(agora)` nesse instante sempre cai no ramo `>= 25`, calculando o mesmo alvo que FR-004 descreve ("mês seguinte ao da execução") — não é uma fórmula nova para o caso agendado, é a mesma fórmula generalizada para qualquer momento. Isso resolve o problema identificado na clarificação: uma verificação de recuperação que só checasse "o ciclo já rodou (sim/não)" não pegaria uma cobrança que falhou isoladamente dentro de um ciclo que "rodou" com sucesso parcial; calcular o mês-alvo e checar idempotência **por cobrança** (FR-006) resolve tanto o ciclo inteiramente perdido quanto a falha isolada, com a mesma chamada de método.
- **Alternatives considered**: dois métodos separados (`generateScheduled()` / `generateOnStartup()`) com lógicas próprias de cálculo de alvo — rejeitado por duplicar a mesma regra de negócio (cálculo de mês-alvo) em dois lugares, com risco real de divergência silenciosa entre eles; guardar um "último ciclo processado com sucesso" em uma tabela de controle separada — rejeitado por complexidade desproporcional quando a checagem por cobrança (já necessária para FR-006) já resolve o mesmo problema sem estado adicional.

## Isolamento por cobrança (FR-016) exige que o método orquestrador NÃO seja `@Transactional` — divergência deliberada do critério padrão do Princípio II

- **Decision**: `generatePendingAccounts()` (o laço sobre todas as cobranças ativas) **não** é anotado `@Transactional`, mesmo executando múltiplas escritas. Cada tentativa individual (`generateOne`, dentro de um `try/catch`) também não é `@Transactional` — as duas escritas que ela faz (`accountRepository.save` da conta nova + `recurringChargeRepository.save` limpando a flag de falha) permanecem como duas chamadas de repositório independentes, cada uma atômica por si (comportamento padrão do Spring Data JPA por chamada).
- **Rationale**: Esta é uma divergência **deliberada e necessária** — não uma omissão — do critério objetivo do Princípio II ("método que executa mais de uma escrita MUST ser `@Transactional`"). Envolver o laço inteiro numa única transação violaria diretamente o FR-016 (decidido na clarificação): uma falha ao gerar a conta de uma cobrança marcaria a transação inteira como rollback-only no Spring, desfazendo também as contas de **todas as outras cobranças já geradas com sucesso** no mesmo ciclo — exatamente o comportamento que a usuária rejeitou explicitamente ao escolher "isolado por cobrança" em vez de "tudo ou nada". Quanto às duas escritas de `generateOne` (conta + flag), não usar `@Transactional` ali evita o problema conhecido de auto-invocação do Spring (um método `@Transactional` chamado de dentro da mesma classe, num laço, não passa pelo proxy AOP e a anotação é ignorada silenciosamente) sem precisar introduzir uma segunda classe só para contornar isso; o risco de inconsistência entre as duas escritas é baixo e autocorrigível — se a conta for salva mas a atualização da flag falhar, a cobrança fica com um aviso "preso" indevidamente, mas a própria checagem de idempotência do próximo ciclo (FR-006) já limpa a flag ao encontrar a conta existente (ver "Atualização da flag" abaixo) — nenhum dado financeiro fica inconsistente, só um indicador cosmético de UI.
- **Alternatives considered**: envolver o laço inteiro em `@Transactional` — rejeitado por violar FR-016 diretamente (explicado acima); extrair `generateOne` para um segundo bean Spring só para permitir `@Transactional` via proxy (evitando auto-invocação) — rejeitado por complexidade desproporcional (uma classe nova só para uma anotação, numa gravação cujo pior cenário de inconsistência é cosmético e autocorrigível).

## Atualização da flag `lastGenerationFailed` acontece em dois pontos, não só no `catch`

- **Decision**: A flag é definida `true` no bloco `catch` de `generateOne`. É definida `false` em dois pontos: (a) ao final de `generateOne`, após a conta ser salva com sucesso; (b) no início do laço, quando a checagem de idempotência (FR-006) já encontra uma conta existente para o mês-alvo e a flag ainda está `true` (caso em que uma tentativa anterior, de um ciclo/mês-alvo diferente, havia falhado e nunca foi limpa).
- **Rationale**: O ponto (b) cobre um cenário residual: uma cobrança falha no mês M (flag=true, sem conta de M), mas nenhuma tentativa nova ocorre antes do ciclo seguinte avançar o alvo para M+1 (edge case já documentado no spec — "aquele mês fica definitivamente sem geração automática"); quando M+1 é gerado com sucesso, sem o ponto (b) a flag continuaria `true` para sempre, mesmo a cobrança estando "em dia" a partir de M+1. FR-018 pede que o aviso desapareça "assim que uma tentativa de geração subsequente conseguir gerar" — uma tentativa que resulta em "conta já existe, nada a fazer" para o mês-alvo atual ainda conta como evidência de que a cobrança está funcionando, então a flag deve refletir isso.
- **Alternatives considered**: só limpar a flag dentro do `catch`/sucesso de `generateOne` (sem o ponto b) — rejeitado pelo cenário residual acima, que deixaria um aviso "fantasma" permanente numa cobrança que já voltou a gerar contas normalmente em meses seguintes.

## `RecurringChargeService` (CRUD/versionamento) fica separado de `RecurringChargeGenerationService` (geração automática)

- **Decision**: Duas classes em `com.financas.recurringcharge.domain`: `RecurringChargeService` (create/createForGroup/update/delete/findAll/findById — mesmo formato de `AccountService` para as operações manuais) e `RecurringChargeGenerationService` (agendamento, recuperação na inicialização, geração propriamente dita). Ambas dependem diretamente de `RecurringChargeRepository`; `RecurringChargeGenerationService` também depende de `AccountRepository` (não de `AccountService` — mesmo padrão de "Service depende de Repository de outra entidade diretamente", já usado por `AccountService` com `PartyRepository`/`GroupRepository`/`FundRepository`).
- **Rationale**: São dois conjuntos de responsabilidade genuinamente distintos — um reage a ações da usuária (CRUD via `Controller`), o outro reage ao relógio (`@Scheduled`) ou ao ciclo de vida da aplicação (`ApplicationReadyEvent`) — juntar os dois na mesma classe misturaria dependências (ex.: `RecurringChargeService` não precisaria de `AccountRepository` para nada além da geração) e tornaria os testes de cada parte menos focados. Não introduz uma camada nova nem um pacote novo — as duas classes continuam em `domain/`, mesmo padrão de múltiplos `Service`s dentro do mesmo pacote de entidade.
- **Alternatives considered**: um único `RecurringChargeService` com todos os métodos — rejeitado pela mistura de responsabilidades acima; mover a geração para dentro de `AccountService` (já que ela cria `Account`s) — rejeitado porque a orquestração depende de dados e regras de `RecurringCharge` (mês-alvo, flag de falha, cobranças ativas) mais do que de `Account` em si; `AccountService` ganharia uma dependência de `RecurringChargeRepository` só para isso.

## Edição (FR-008) cria uma nova linha e inativa a anterior — sem `@Transactional` explícito adicional além do já exigido pelo Princípio II

- **Decision**: `RecurringChargeService.update(id, ...)` é `@Transactional` (duas escritas: `save` da linha antiga com `deactivatedAt=LocalDate.now()`, `save` da linha nova com `deactivatedAt=null`), mesmo critério já usado por `AccountService.registerPayment` no ramo de split. Retorna a linha nova (com um `id` diferente do informado na URL) — o `Controller`/DTO de resposta não fingem que o `id` permanece o mesmo.
- **Rationale**: Segue diretamente o critério objetivo do Princípio II (≥2 escritas sequenciais numa única operação de negócio). O frontend já navega de volta para a listagem após qualquer submissão de formulário bem-sucedida (mesmo padrão de `AccountForm`/`PartyForm`), então o `id` mudar não exige nenhum tratamento especial de UI — a usuária nunca fica "presa" numa tela de edição apontando para um `id` que deixou de ser a versão vigente.
- **Alternatives considered**: manter o mesmo `id` e só marcar a linha antiga como uma "versão histórica" separada, com um campo de encadeamento (`previousVersionId`) — explicitamente rejeitado pelo próprio spec (Assumptions: "não é necessário nenhum mecanismo de encadeamento entre versões").

## Bloqueio de remoção de `Party`/`Fund` com cobrança recorrente ativa (FR-014) reaproveita o padrão de `PartyHasAccountsException`/`FundHasAccountsException`, com exceptions novas e dedicadas

- **Decision**: `PartyService`/`FundService` ganham uma dependência nova de `RecurringChargeRepository`, com um método `existsByPartyIdAndDeactivatedAtIsNull`/`existsByFundIdAndDeactivatedAtIsNull` (query derivada do Spring Data, coerente com o campo `deactivatedAt` — ver decisão acima), chamado em `delete()` antes do `deleteById` já existente. Duas exceptions novas — `PartyHasActiveRecurringChargesException` (em `party.domain`) e `FundHasActiveRecurringChargesException` (em `fund.domain`) — em vez de generalizar as exceptions já existentes (`PartyHasAccountsException`/`FundHasAccountsException`) para uma mensagem genérica.
- **Rationale**: Mensagens de erro específicas ("possui cobranças recorrentes ativas" vs. "possui contas vinculadas") são mais úteis à usuária do que uma mensagem genérica que não diferencia os dois motivos de bloqueio. Cada exception continua vivendo no `domain/` da entidade que ela protege (`Party`/`Fund`), conforme o Princípio I exige para exceptions que representam regra de negócio específica de uma entidade.
- **Alternatives considered**: generalizar `PartyHasAccountsException` para cobrir os dois motivos (`"possui contas ou cobranças recorrentes vinculadas"`) — rejeitado por perder precisão informativa sem ganho real de simplicidade (a lógica de decisão em `delete()` continuaria precisando checar as duas condições separadamente de qualquer forma).

## Validação de `amount` (não-negativo) espelha `Account`; validação de `dueDay` (1–31) fica só em Bean Validation

- **Decision**: `RecurringChargeService` ganha `validateNonNegativeAmount` + `InvalidRecurringChargeAmountException extends BadRequestException`, reusado em `create`/`createForGroup`/`update` — mesmo padrão de `AccountService`. `dueDay` é validado só via Bean Validation (`@Min(1) @Max(31)`) nos DTOs (`RecurringChargeRequest`/`RecurringChargeBulkRequest`), sem checagem duplicada no `Service`.
- **Rationale**: `amount` segue o precedente direto de `Account` para a mesma regra de negócio ("valor não pode ser negativo"), reaplicada em `create`/`createForGroup`/`update` — critério que a Constituição já aceita como suficiente para justificar reforço no `Service`. `dueDay` é um campo novo, puramente sintático (validação de faixa, sem depender de outro campo ou de estado do banco) e usado nos mesmos dois DTOs que já validam esse tipo de regra independentemente — não há nenhum caminho de criação de `RecurringCharge` que contorne a validação do DTO (diferente de `Account`, que tem `duplicate`/`registerPayment` construindo objetos sem passar por um DTO validado), então Bean Validation sozinha já é suficiente pelo próprio critério da Constituição.
- **Alternatives considered**: checagem de `dueDay` também no `Service` — rejeitada por não haver caminho de bypass do DTO para `RecurringCharge` (diferente de `Account`), tornando a duplicação só uma redundância sem função defensiva real.

## Cobertura de teste automatizado desta feature

- **Decision**: Backend — `RecurringChargeServiceTest` (JUnit 5 + Mockito, mesmo padrão de `AccountServiceTest`/`PartyServiceTest`) cobrindo: criação (parte específica e grupo, incluindo grupo vazio), valor R$0,00 aceito, valor negativo rejeitado, imutabilidade do tipo na edição, edição criando nova versão e inativando a anterior, remoção como soft delete, listagem excluindo inativas. `RecurringChargeGenerationServiceTest` cobrindo: geração básica (múltiplas cobranças ativas → múltiplas contas, cada uma referenciando o molde), idempotência (segunda execução no mesmo ciclo não duplica), ajuste de dia de vencimento em mês curto, ausência de cobranças ativas (sem erro), isolamento (uma cobrança falha, as demais são geradas), atualização da flag `lastGenerationFailed` (definida no catch, limpa no sucesso, limpa quando já existia conta), cálculo do mês-alvo (`resolveMostRecentDueTargetMonth`) para datas antes/depois do dia 25. `PartyServiceTest`/`FundServiceTest` ganham casos novos para o bloqueio de remoção com cobrança recorrente ativa. Frontend — validação manual via Playwright (devDependency já configurada), sem testes unitários dedicados a componentes novos (mesmo precedente já registrado nas features 006/007/008).
- **Rationale**: Mantém a mesma linha divisória já usada no projeto entre "lógica de negócio pura, testada por JUnit/Mockito" e "orquestração de componente Angular, validada via Playwright". Cobertura de regra de negócio nova é exigência explícita do Princípio III, reforçada para esta feature por tocar dinheiro (geração de contas) e por ter um mecanismo de recuperação/idempotência cujo comportamento incorreto seria difícil de perceber manualmente.
- **Alternatives considered**: testar `@Scheduled`/`ApplicationReadyEvent` via `@SpringBootTest` de integração, esperando o disparo real do agendamento — rejeitado por ser lento e frágil (dependeria de manipular o relógio do sistema ou esperar minutos); testar `generatePendingAccounts()` diretamente, chamado pelo teste como um método de negócio comum, já cobre toda a lógica relevante sem depender da infraestrutura de agendamento do Spring.
