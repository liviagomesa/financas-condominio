Geração automática de contas recorrentes via cron mensal. 

Nova entidade "cobrança/pagamento recorrente" (molde), separada de `Account`: cada linha representa uma cobrança ou pagamento fixo e recorrente de uma contraparte específica — uma linha por contraparte (`Party`), não um "plano" compartilhado por várias contrapartes ao mesmo tempo (a escala do projeto é de dezenas/centenas de unidades, não milhares, e cada contraparte pode legitimamente ter valor, dia de vencimento ou observações diferentes das demais, então a edição precisa continuar sendo por linha). Campos: tipo (mesmo discriminador receber/pagar de `Account`, obrigatório na criação e imutável na edição), valor fixo, dia do mês de vencimento (não uma data completa — o dia é combinado com o mês/ano no momento da geração, com ajuste para o último dia do mês em meses mais curtos), descrição, fundo, contraparte (`Party`), observações opcionais.

Ao criar essa cobrança/pagamento recorrente, devo poder escolher entre lançar para parte específica ou para grupo, como tem no formulário de nova conta hoje.

A geração mensal precisa ser idempotente (não duplicar caso o job rode mais de uma vez no mesmo período, por exemplo após um redeploy) — a conta gerada guarda uma referência de volta para o molde que a originou, permitindo checar diretamente se já existe uma conta gerada daquele molde para o mês/ano alvo, em vez de tentar inferir isso comparando outros campos.

Editar o valor de uma cobrança recorrente (o reajuste anual mencionado no README do produto) NÃO deve alterar o valor de contas já geradas no passado — a edição preserva o histórico substituindo a linha atual por uma nova versão (a antiga deixa de ser considerada ativa, mas continua existindo, referenciada pelas contas já geradas a partir dela), em vez de sobrescrever o valor em uma única linha mutável. Não é necessário nenhum mecanismo de encadeamento entre versões (sem campo tipo "versão anterior" ou identificador de linhagem compartilhado) — o histórico de valores ao longo do tempo já fica implicitamente registrado nas próprias contas geradas mês a mês. Quando uma contraparte deixa de ter a cobrança recorrente (ex.: condômino que saiu), a remoção também não deve ser uma exclusão física — precisa preservar a linha e as contas já geradas a partir dela, apenas parando de gerar novas contas dali em diante. Isso provavelmente significa que ao deletar uma cobrança recorrente, o sistema implementa soft delete. O registro deixa de aparecer nas listagens, mas a FK não quebra.

O job de geração roda automaticamente todo dia 25 de cada mês, às 6h da manhã (horário de Brasília), gerando as contas referentes ao mês seguinte a partir de todas as cobranças recorrentes ativas no momento da execução. Precisa haver também uma tela de gerenciamento (listar, criar, editar, remover) dessas cobranças recorrentes, reaproveitando os padrões de UI já estabelecidos no projeto para outras listagens (ações de linha, seleção múltipla).

Existem casos de cobrança recorrente sem valor fixo. Nesses casos, criarei a recorrência com valor de R$0,00 e fico responsável por alterar os valores da instância depois manualmente.
